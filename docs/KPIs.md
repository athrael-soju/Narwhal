# Serving KPIs

Narwhal separates prefill and decode quality because they describe different
parts of the user experience and consume different fleet capacity. Measure both
for every run. Throughput by itself can conceal a fleet that is serving many
requests too slowly.

## Primary latency metrics

| KPI                | What it measures                                                                                             | Formula                                                      | Main capacity phase  |
| ------------------ | ------------------------------------------------------------------------------------------------------------ | ------------------------------------------------------------ | -------------------- |
| TTFT               | Time to first token: how long the user waits for generation to begin                                         | prefill queue delay + prefill compute                        | Prefill              |
| TPOT / ITL         | Time per output token, also called mean inter-token latency: how smoothly a response streams after it begins | `(last token time - first token time) / (output tokens - 1)` | Decode               |
| First-byte latency | The client-visible wait until the streaming response first arrives                                           | TTFT + KV transfer + decode queueing                         | The P/D handoff path |
| End-to-end latency | Time from request arrival to the completed response                                                          | first-byte latency + remaining generation time               | Both                 |

TTFT ends when the prefill instance produces `o1`. It is a prefill-quality
metric, so a high TTFT generally means prefill queues, long prompts, or too
little prefill capacity. The router journals this value as `ttft_s`.

TPOT is the mean gap between output tokens generated by the same decode
instance. It is `null` for a response with fewer than two output tokens,
because it has no token-to-token gap. A high TPOT generally means decode
pressure, such as excessive batching or insufficient decode capacity. The
router journals this value as `tpot_s`.

`first_byte_s` is not the same as `ttft_s`. It measures what the client sees,
and can be longer because a disaggregated request may transfer its KV cache and
wait for decode after prefill completes. Use it to investigate client
experience. Use TTFT and TPOT to identify which serving phase needs capacity.

## SLO attainment and goodput

Set separate SLOs for TTFT and TPOT. A request attains the serving SLO only
when it completes its requested output and meets both targets:

```
complete request
and ttft_s <= TTFT SLO
and tpot_s <= TPOT SLO
```

**SLO attainment** is the percentage of offered requests that satisfy that
condition. Report its rate with TTFT and TPOT percentiles, because averages
hide tail latency. The shipped Prometheus histograms carry both
distributions; `narwhal-report`'s own percentile table covers the KV
handoff.

**Goodput** is the highest sustained request rate that reaches the chosen
attainment target, normally 90%, while meeting both TTFT and TPOT SLOs. It is
the headline capacity metric because it counts only completed, timely work.
Raw throughput can rise while goodput falls when a fleet accepts more work than
it can serve within its latency budgets.

For interactive chat and code completion, a tight TTFT avoids an initial pause
and a tight TPOT preserves smooth streaming. Long summarization workloads can
usually tolerate a looser TTFT budget, but still need enough decode capacity to
maintain their TPOT target.

## Operational diagnostics

| KPI                              | Why it matters                                                                                                                      |
| -------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------- |
| Error and short-response rate    | Errors and outputs short of `wanted_len` miss goodput regardless of their latency.                                                  |
| Prefill/decode pool load         | Each pool's pressure relative to its SLO-based target. Values above `1.0` are over the modeled budget.                              |
| Resident requests / queue depth  | Leading indicator of pressure on an instance or phase; diagnose alongside TTFT and TPOT, rather than treating it as a user outcome. |
| KV-transfer time                 | Attributes crossed prefill/decode handoff cost separately from compute and queueing.                                                |
| Re-role events and time-to-adapt | Shows whether the adaptive controller responds promptly when the workload's phase mix changes.                                      |
| Flip reversals (thrash)          | Detects unstable P/D role changes that undo each other.                                                                             |
| Requests resident during a flip  | Quantifies work exposed to a re-role operation and its potential latency cost.                                                      |
| Ejected instances                | Nonzero means the breaker currently excludes capacity from scheduling; treat it as an availability signal.                          |
| Placement regret                 | Scheduling-efficiency diagnostic relative to the placement's own lower-bound cost.                                                  |

The request journal is the source of record for request-level KPIs. See
[Api](Api.md) for its fields and `narwhal-bench --score-journal` for scoring a
recorded run against the configured SLOs.
